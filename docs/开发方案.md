# 时间簿 · 开发方案

> 版本：v1.0（2026-11-16）
> 依据：已定稿的交互原型（今日 / 日历 / 统计 / 标签四页）以及前期需求讨论。
> 目标读者：负责开发的人（包括未来的自己）。看完这份文档，应该能直接开始写代码。

---

## 1. 项目概述

**时间簿**是一个个人用的时间记录与可视化工具，用来替代原来在 Notion 里搭的「个人时间可视化管理」工作区。

Notion 版本的主要问题：

- 日报、周报要手动点「归档」才有统计，累计数据经常是旧的。
- 记录、标签、统计之间靠关联和公式拼起来，改一处容易坏一片。
- 不能同时开多个计时，补记录要手改开始结束时间，很麻烦。
- 页面没法做个性化设计，也不好看。

新工具的原则：

1. **只存三类原始数据**：标签、专注记录、待办。所有日报、周报、月报、年报、累计都由原始数据**实时计算**，不再有"归档"。
2. **记录是独立的**：任意时刻可以有多条进行中的计时，开始新的不会结束旧的。
3. **补记录要顺手**：系统主动指出漏记的时间段，一点就补。
4. **多设备一致**：手机、电脑看到的是同一份数据，进行中的计时也同步。
5. **随时知道数据是否安全**：右上角「数据已同步」状态就是断联监控。

使用者：只有一个人（我自己），不做账号体系，但要防止别人访问。

## 2. 功能范围

### 2.1 第一版（MVP）必须有

| 模块 | 功能 |
| --- | --- |
| 今日 | 今日四个模块用时；待办列表（新增、完成、开始这件事）；进行中的计时（可多个，结束 / 取消 / 换标签）；时间线（按天切换、空档提示、补记录、编辑 / 删除记录） |
| 计时 | 先开始再选标签（可「稍后再选」）；从待办开始时自动带上标签和标题 |
| 日历 | 周视图；在空白处拖动补记录；点色块编辑；切换周 |
| 统计 | 日 / 周 / 月 / 年；模块与具体事项两个维度；环形图、排行、趋势柱状图；与上一周期对比 |
| 标签 | 模块（一级）与事项（二级）的新建、修改、删除；删除时迁移或一并删除记录；模块颜色 |
| 数据 | 从 Notion 导入历史；全部数据导出（JSON / CSV） |
| 状态 | 「数据已同步」断联监控 |
| 访问 | 访问口令登录；HTTPS |

### 2.2 第一版可以先简化，第二版再做

- 重复待办的复杂规则（第一版支持：每天、每周几、每月几号）。
- 离线时继续使用（第一版：断网时提示并暂存本机，恢复后补传；第二版：完整离线可用）。
- 手机端的拖动补记录（第一版手机上用「补记录」按钮，桌面端支持拖动）。
- 「忘记结束计时」的提醒。

### 2.3 明确不做

- 多用户、团队、分享。
- 番茄钟、白噪音等专注辅助功能。
- 原 Notion 里的「归档」按钮、手动刷新的「今天累计」等。

## 3. 业务规则（开发时以这里为准）

### 3.1 时间与周期

- **时区**：所有时间在数据库里按 UTC 毫秒时间戳存储；"一天从几点开始"按设置里的时区计算（默认 `Asia/Shanghai`，可在设置里改）。
- **日**：自然日，00:00–24:00。
- **周**：自然周，**周一开始**。
- **月**：自然月，**1 号开始**。
- **年**：自然年。

### 3.2 专注记录（Session）

- 一条记录 = 开始时间 + 结束时间 + 事项标签（可为空）+ 标题（可选）+ 来源待办（可选）。
- **进行中**的记录：结束时间为空。
- **多个计时可以同时进行**，互不影响。开始新计时**不会**结束任何已有计时。
- **开始专注**：立即开始计时，然后弹出标签选择；可以「稍后再选」。没选标签的计时，结束时必须补选标签（或保存到「未分类」，统计里单独显示，见 3.6）。
- **从待办开始**：直接带上待办的标签和标题，不弹选择框。
- **取消**：删除这条进行中的记录，不留痕迹。
- **结束**：结束时间 = 点击时刻。
- **补记录 / 编辑**：可以改标签、日期、开始、结束时间。
  - 结束时间早于开始时间时，视为**跨到次日**。
  - 时长必须大于 0；单条记录上限 24 小时（超过时提示，可能是输错了）。
  - **允许与其他记录重叠**，只给出提示，不阻止保存。

### 3.3 跨天记录的统计口径

一条记录如果跨过 0 点（比如 23:00–01:30），**按实际时间切分**：前一天算 1 小时，后一天算 1.5 小时。周、月、年同理。

> 原型里为了简单，把跨天记录整条算在开始那天，开发时以本条为准。

### 3.4 同时进行的记录怎么算总时长

- 模块 / 事项的时长：每条记录各自累加。比如 14:00–15:00 同时在「工作」和「游戏」，工作 +1 h，游戏 +1 h。
- 「总时长」也按累加计算，所以理论上一天的总时长可能超过 24 小时。这和 Notion 里的算法一致。
- （可选，第二版）在统计页额外显示「实际占用时间」（把重叠部分去重后的时长）。

### 3.5 空档（漏记提示）

空档用来提示"这段时间可能忘了计时"：

1. 只在**当天两条记录之间**找空档：把当天所有记录（包括进行中的计时，以它的开始时间为准）按时间合并后，相邻两段之间的空白就是候选空档。
2. **短于 20 分钟的空档忽略**。
3. **不根据当前时间推测空档**：最后一条记录结束后、下一条还没开始之前，这段时间不算空档。只有等下一条记录出现（开始计时或补了一条），中间的空白才会被标出来。
4. 一天第一条记录之前（比如睡觉时间）不算空档。
5. 空档在时间条上显示为橙色斜纹块，在列表里显示为「没有记录 · 时长」并带「+ 补上」；点击后打开补记录，开始和结束时间直接填成空档的起止。
6. 空档只是提示，不存进数据库，随记录变化实时重新计算。

### 3.6 标签（模块 / 事项）

- 两级：**模块**（一级，如工作、学习、游戏、锻炼）下面挂**事项**（二级，如淘教、Python、星穹铁道）。
- 记录只关联**事项**；模块时长 = 模块下所有事项时长之和。
- **颜色只属于模块**，事项沿用所属模块的颜色（统计里用深浅区分同模块的事项）。
- 模块颜色从 8 个预设色里选（见设计规范），不能自定义任意色，保证整体协调。两个模块选同一个颜色时给出提醒。
- 同一模块下事项不能重名。
- **修改事项的所属模块**：过去的记录跟着事项一起算到新模块。
- **删除事项**：
  - 没有记录 → 直接删除。
  - 有记录 → 二选一：① 把记录改到另一个事项下（推荐，总时长不变）；② 连同记录一起删除（提示会少掉多少小时）。
- **删除模块**：
  - 空模块 → 直接删除。
  - 有事项 → 二选一：① 把事项移到另一个模块；② 连同事项和记录一起删除。
- 所有删除都是**软删除**（打 `deleted_at` 标记），30 天内可以在设置里恢复，便于误删找回和多设备同步。
- 「未分类」：没有选标签就结束的计时，统计里显示为灰色的「未分类」，可在时间线里点开补标签。

### 3.7 待办

- 字段：标题、事项标签、计划日期（哪天做，对应 Notion 的「执行日期」）、截止日期（可选）、重复规则（可选）、完成状态。
- **今日页显示哪些待办**：计划日期 ≤ 今天且未完成的；没有计划日期的也显示；今天完成的显示在末尾（变淡、划线）。
- **开始这件事**：创建一条进行中的记录，标签和标题取自待办，并记下来源待办。
- **已投入**：显示与这条待办关联的记录总时长。重复待办显示**本次**（今天这一轮）投入的时长。
- **重复待办**（第一版）：
  - 规则：每天 / 每周的某几天 / 每月某几号。
  - 每一轮单独记完成状态。今天这一轮完成后，今天显示为已完成；到下一个符合规则的日期，自动出现新的一轮。
  - 错过的轮次**不累积**（比如周一没做，周三不会出现两条）。
- 截止日期临近时显示倒计时（如「还剩 2 天」，过期显示「已过期 1 天」）。

### 3.8 「数据已同步」断联监控

右上角的状态表示**工具是否正常运行、数据是否已安全写入数据库**：

| 状态 | 什么时候出现 | 样式 |
| --- | --- | --- |
| 数据已同步 | 所有改动都已写入数据库，且最近一次心跳成功 | 青绿色圆点，轻微呼吸动画 |
| 正在保存… | 有改动正在提交 | 黄色圆点 |
| 连接断开 · N 条待保存 | 心跳失败或请求失败；改动暂存本机 | 橙色胶囊，醒目 |
| 数据库异常 | 服务能连上，但健康检查里数据库读写失败 | 橙色胶囊 + 提示「数据可能没有保存」 |

- 鼠标悬停 / 点击时显示详情：上次成功保存的时间、待保存条数、错误原因、「立即重试」按钮。
- 心跳：前台每 30 秒请求一次 `/api/health`，页面重新获得焦点时立刻请求一次。
- 健康检查在服务端真实地读写数据库一次（写一行心跳时间），而不是只返回 200。
- 断开期间的改动进入本机「待发送队列」，恢复后按顺序补传；补传完成前状态不会显示为「已同步」。
- （可选）在外部用免费的 UptimeRobot 之类监控 `/api/health`，服务挂了推送到手机。

## 4. 页面与交互要点

原型已经覆盖了主要交互，这里只补充开发时容易漏的细节。

### 4.1 今日

- 顶部日期 + 四个模块今日用时（包含进行中的计时，每分钟刷新）。
- 「开始专注」是全页唯一的大黄色按钮。
- 待办卡片：「开始这件事」平时浅灰，悬停变黄。
- 进行中的计时卡：整卡用模块浅底色；计时每秒刷新；显示开始时刻。
- 时间线卡：‹ › 切换日期（不能切到未来）；空档规则见 3.5；点记录编辑；「补记录」默认填入最近一个空档，没有空档则留空。

### 4.2 日历

- 周视图显示 06:00–24:00，06:00 之前的记录在顶部用一条细栏提示（"有 1 条 06:00 前的记录"，点开可编辑）。
- 在空白处按下并拖动，以 15 分钟为单位吸附；松手打开补记录。只点一下不拖，默认 1 小时。
- 未来的日期不能拖动补记录。
- 同一时段的多条记录并排显示。

### 4.3 统计

- 日 / 周 / 月 / 年切换，‹ › 翻页，不能翻到未来。
- 四个数字卡：总时长（与上一周期对比）、日均（按已过去的天数算）、花得最多、专注次数。
- 「时间花在哪」：模块 / 具体事项切换；环形图 + 排行（时长、占比、条形）。
- 趋势：日看每小时，周和月看每天，年看每月；按模块分色叠加。

### 4.4 标签

- 鼠标悬停显示修改、删除按钮（手机上常显）。
- 弹窗规则见 3.6。

### 4.5 手机端

- 底部四个标签栏（今日 / 日历 / 统计 / 标签）替代顶部导航；「数据已同步」状态放在页面右上角。
- 今日页：有进行中的计时时，屏幕底部常驻一条迷你计时条（显示个数和最长的一条，点开展开）。
- 日历：默认 3 天视图，可切单日；第一版用「补记录」按钮，第二版支持长按拖动。
- 统计：卡片纵向堆叠。
- 支持「添加到主屏幕」（PWA），全屏打开像 App 一样。

## 5. 技术架构

### 5.1 总体结构

```
浏览器（电脑 / 手机 PWA）
  ├─ 前端：React 单页应用
  ├─ 本机缓存：IndexedDB（全部数据的副本 + 待发送队列）
  └─ 统计、空档、重复待办全部在前端实时计算
          │  HTTPS + 登录 Cookie
          ▼
服务端 API（Hono）
  ├─ 鉴权、读写、增量同步、健康检查、导入导出
  └─ 数据库：SQLite（Cloudflare D1 或 NAS 上的 SQLite 文件）
```

为什么统计放在前端算：个人数据量很小（一年大约 1,500–3,000 条记录），全部放在本机内存里算只需要几毫秒，切换周期和维度不用等网络；并且断网时也能看统计。

### 5.2 技术选型

| 部分 | 选择 | 理由 |
| --- | --- | --- |
| 语言 | TypeScript（前后端统一） | 类型共享，规则代码只写一份 |
| 前端框架 | React 18 + Vite | 生态成熟，原型可以直接翻译成组件 |
| 状态管理 | Zustand | 轻量 |
| 本机存储 | Dexie（IndexedDB） | 离线缓存与待发送队列 |
| 日期处理 | date-fns + date-fns-tz | 自然周（周一开始）、时区 |
| 图表 | 手写 SVG（同原型） | 只有环形图和柱状图，不值得引入图表库，样式完全可控 |
| PWA | vite-plugin-pwa | 添加到主屏幕、静态资源缓存 |
| 服务端框架 | Hono | 同一份代码可以跑在 Cloudflare Workers 和 Node（NAS）上 |
| 数据库访问 | Drizzle ORM | 同时支持 D1 与 better-sqlite3，迁移脚本统一 |
| 校验 | Zod | 前后端共用数据结构校验 |
| 测试 | Vitest（规则与统计）+ Playwright（关键流程） | |
| 包管理 | pnpm workspace | 单仓多包 |

### 5.3 仓库结构

```
timebook/
├─ apps/
│  ├─ web/            # 前端
│  └─ api/            # 服务端（Hono），含 Workers 与 Node 两个入口
├─ packages/
│  └─ core/           # 共享：类型、Zod 结构、统计 / 空档 / 重复规则 / 时间切分等纯函数（重点测试）
├─ tools/
│  └─ notion-import/  # Notion CSV 解析与映射（前端导入页也复用它）
├─ prototype/         # 原型源码（Claude 设计画布导出，仅供参考）
└─ docs/              # 本文档、设计规范、截图
```

### 5.4 部署方案对比

| | 方案 A：Cloudflare（推荐） | 方案 B：自家 NAS |
| --- | --- | --- |
| 组成 | Pages（前端）+ Workers（API）+ D1（数据库） | 一个 Docker 容器（Node + SQLite 文件）+ 内网穿透 |
| 费用 | 个人用量在免费额度内 | 无额外费用 |
| 稳定性 | 7×24 在线，不受家里断电断网影响 | 依赖 NAS 和家庭网络、穿透服务 |
| HTTPS | 自动 | 需要穿透服务或反向代理配置证书 |
| 备份 | D1 自带 30 天时间点恢复 + 定时导出 | 需要自己做（见第 9 节），可配合 NAS 快照 |
| 数据位置 | Cloudflare 云端 | 自己家里 |
| 国内访问 | `*.workers.dev` / `*.pages.dev` 在国内经常打不开，**需要绑定自己的域名**，速度一般 | 取决于穿透服务，通常更稳 |

**建议**：如果主要在国外网络环境使用，或者手里有域名，选方案 A，省心；如果主要在国内使用、没有域名，选方案 B。两种方案用的是同一份代码，后期可以迁移（导出 / 导入即可）。也可以组合：主服务在 Cloudflare，NAS 每天拉取一份备份。

> 这是需要你拍板的第一个问题，见第 12 节。

## 6. 数据模型

所有表都有 `created_at`、`updated_at`（服务端写入，UTC 毫秒）、`deleted_at`（软删除）。主键用客户端生成的 ULID（可以离线创建、按时间有序）。

```sql
-- 模块（一级标签）
CREATE TABLE modules (
  id          TEXT PRIMARY KEY,
  name        TEXT NOT NULL,
  color_key   TEXT NOT NULL,          -- blue / violet / teal / rose / amber / sky / green / pink
  sort        INTEGER NOT NULL DEFAULT 0,
  created_at  INTEGER NOT NULL,
  updated_at  INTEGER NOT NULL,
  deleted_at  INTEGER
);

-- 事项（二级标签）
CREATE TABLE tags (
  id          TEXT PRIMARY KEY,
  module_id   TEXT NOT NULL REFERENCES modules(id),
  name        TEXT NOT NULL,
  sort        INTEGER NOT NULL DEFAULT 0,
  created_at  INTEGER NOT NULL,
  updated_at  INTEGER NOT NULL,
  deleted_at  INTEGER
);
CREATE UNIQUE INDEX tags_module_name ON tags(module_id, name) WHERE deleted_at IS NULL;

-- 专注记录
CREATE TABLE sessions (
  id          TEXT PRIMARY KEY,
  tag_id      TEXT REFERENCES tags(id),       -- 可为空：未分类
  todo_id     TEXT REFERENCES todos(id),      -- 从待办开始时记录
  title       TEXT,                           -- 可选，例如「谷米FDE开发」
  start_at    INTEGER NOT NULL,               -- UTC 毫秒
  end_at      INTEGER,                        -- 为空 = 进行中
  note        TEXT,
  source      TEXT NOT NULL,                  -- timer / manual / import
  import_batch TEXT,                          -- 导入批次，便于整批撤销
  created_at  INTEGER NOT NULL,
  updated_at  INTEGER NOT NULL,
  deleted_at  INTEGER
);
CREATE INDEX sessions_start ON sessions(start_at);
CREATE INDEX sessions_running ON sessions(end_at) WHERE end_at IS NULL;

-- 待办
CREATE TABLE todos (
  id          TEXT PRIMARY KEY,
  title       TEXT NOT NULL,
  tag_id      TEXT REFERENCES tags(id),
  plan_date   TEXT,                           -- YYYY-MM-DD，计划哪天做
  due_date    TEXT,                           -- YYYY-MM-DD，截止日期
  recur       TEXT,                           -- JSON，见下；为空 = 一次性
  done_at     INTEGER,                        -- 一次性待办的完成时间
  sort        INTEGER NOT NULL DEFAULT 0,
  created_at  INTEGER NOT NULL,
  updated_at  INTEGER NOT NULL,
  deleted_at  INTEGER
);
-- recur 示例：
-- {"freq":"daily"}
-- {"freq":"weekly","days":[1,3,5]}        // 周一、三、五（1=周一 … 7=周日）
-- {"freq":"monthly","monthDays":[1,15]}

-- 重复待办的每一轮完成情况
CREATE TABLE todo_checks (
  todo_id     TEXT NOT NULL REFERENCES todos(id),
  date        TEXT NOT NULL,                  -- 这一轮对应的日期
  done_at     INTEGER NOT NULL,
  updated_at  INTEGER NOT NULL,
  deleted_at  INTEGER,
  PRIMARY KEY (todo_id, date)
);

-- 设置（时区等）
CREATE TABLE settings (
  key         TEXT PRIMARY KEY,
  value       TEXT NOT NULL,
  updated_at  INTEGER NOT NULL
);

-- 健康检查写入的心跳
CREATE TABLE heartbeat (
  id          INTEGER PRIMARY KEY CHECK (id = 1),
  at          INTEGER NOT NULL
);
```

## 7. 服务端接口

所有接口在 `/api` 下，除登录和健康检查外都需要登录 Cookie。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/login` | 提交访问口令，成功后设置 Cookie |
| POST | `/api/logout` | 退出当前设备 |
| GET | `/api/health` | 健康检查：真实读写一次数据库，返回 `{ ok, db, serverTime }` |
| GET | `/api/sync?since=<ts>` | 增量拉取：返回 `since` 之后有变化的所有行（含软删除），以及新的游标 |
| POST | `/api/mutations` | 批量提交本机改动（待发送队列），每条带客户端 ID，保证重复提交不会重复写入 |
| GET | `/api/export?format=json\|csv` | 导出全部数据 |
| POST | `/api/import/notion` | 提交解析好的导入数据（批次） |
| DELETE | `/api/import/:batch` | 撤销某次导入 |

为什么用「增量同步 + 批量提交」而不是一个个 REST 接口：前端所有写操作都先进入本机队列再发送，天然支持断网暂存和自动补传，也让「数据已同步」状态有据可依。

## 8. 同步、离线与断联监控

1. **启动**：首次登录时全量拉取，存入 IndexedDB；之后每次打开只做增量拉取。
2. **写入**：任何改动（开始计时、补记录、改标签……）先写本机并立即更新界面，同时放进待发送队列，再提交到服务端。
3. **提交成功**：从队列移除，用服务端返回的 `updated_at` 覆盖本机。
4. **提交失败**：保留在队列，状态变成「连接断开 · N 条待保存」，之后按 2s、5s、15s、30s… 重试，心跳恢复时立刻重试。
5. **拉取**：每 30 秒（和心跳一起）以及页面重新获得焦点时拉取一次，多设备之间最多延迟 30 秒；进行中的计时也通过这种方式同步到其他设备。
6. **冲突**：单人使用，冲突很少。按行比较 `updated_at`，后写的覆盖先写的；被覆盖时不提示。
7. **进行中的计时**：本质就是 `end_at` 为空的记录，计时显示 = 当前时间 − `start_at`，不依赖某台设备一直开着页面。电脑上开始、手机上结束完全没问题。
8. **时钟偏差**：每次心跳返回服务端时间，前端记录偏差，开始 / 结束计时时用校正后的时间。

## 9. 安全与备份

### 9.1 访问控制

- 单用户，**访问口令**登录（长随机串，存在服务端环境变量里，不进仓库）。
- 登录成功后下发签名 Cookie（HttpOnly、Secure、SameSite=Lax，有效期 180 天），每台设备登录一次即可。
- 登录接口限流（例如每 IP 每分钟 5 次），防止暴力猜测。
- 方案 A 可以额外套一层 Cloudflare Access（邮箱验证码），双保险。

### 9.2 备份

- **随时手动导出**：设置页「导出全部数据」（JSON，含所有表；以及 CSV，方便用 Excel 看）。
- **方案 A**：D1 自带 30 天时间点恢复；另加一个每日定时任务，把全量 JSON 存到 R2（保留 90 天）。
- **方案 B**：容器内每天凌晨 `sqlite3 .backup` 到挂载目录，保留 30 份；再开启 NAS 自带的快照 / 备份任务异地一份。
- 每月一次：随便挑一份备份恢复到测试环境，确认能用（备份不验证等于没有）。

## 10. Notion 历史数据导入

### 10.1 导出

在 Notion 里分别导出三个数据库为 CSV（「导出」→ 格式选「Markdown & CSV」→ 不包含子页面）：

1. 专注记录
2. 时间标签
3. 待办（可选，只导入未完成的）

### 10.2 字段映射

| Notion | 时间簿 | 说明 |
| --- | --- | --- |
| 时间标签 · 一级标签 | modules | 名称直接用；颜色按名称映射到预设色 |
| 时间标签 · 二级标签 | tags | 挂到对应模块下 |
| 专注记录 · 开始 / 结束 | sessions.start_at / end_at | 按 CSV 中的时区解析；没有结束时间的记录列出来让我确认 |
| 专注记录 · 标签 | sessions.tag_id | CSV 里是「名称 (链接)」格式，按名称匹配；匹配不上的列出来手动指定 |
| 专注记录 · 待办 | sessions.title | 只保留文字作为标题，不建立关联 |
| 待办 · 事项 / 执行日期 / 截止日期 / 状态 | todos | 只导入未完成的 |

### 10.3 导入流程（做成设置里的一个页面）

1. 上传 CSV（可一次传多个）。
2. 自动解析，显示**预览**：识别到多少条记录、时间范围、每个模块的总时长。
3. 列出**问题项**：标签匹配不上、缺少结束时间、时长超过 24 小时、开始晚于结束等，逐条或批量处理。
4. **核对**：把各模块的历史总时长和 Notion 里「累计」页面的数字对比（例如工作 58,283 min、游戏 33,291 min、学习 20,988 min），差异在 1% 以内再确认导入。
5. 确认导入，生成一个**导入批次**；不满意可以整批撤销重导。

## 11. 开发里程碑

| 阶段 | 内容 | 完成标准 |
| --- | --- | --- |
| M0 搭骨架 | 仓库结构、前后端空项目、数据库迁移、登录、健康检查；部署到选定环境 | 手机和电脑都能用口令登录，看到「数据已同步」 |
| M1 记录与标签 | 标签增删改（含迁移）；开始 / 结束 / 取消计时；多计时并行；标签选择；同步队列 | 电脑开始的计时，手机上能看到并结束 |
| M2 今日页 | 待办（含重复）；时间线、空档、补记录、编辑记录 | 按原型完整走通今日页所有交互 |
| M3 日历与统计 | 周视图与拖动补记录；统计四个周期两个维度；跨天切分 | 统计数字通过单元测试，与手算一致 |
| M4 导入导出 | Notion CSV 导入页；导出；备份任务 | 历史数据导入后与 Notion 累计数字对得上 |
| M5 手机与打磨 | 手机布局、PWA、断网补传、各种空状态和错误提示、动效 | 手机上加到主屏幕后日常使用一周无问题 |

建议顺序做，每个阶段结束都部署一次，边用边改。M1 完成后就可以开始和 Notion 并行记录。

### 必须写单元测试的纯函数（放在 `packages/core`）

- 自然周 / 月 / 年的起止计算（含时区、周一开始）
- 跨天记录按天切分
- 各周期、各维度的汇总
- 空档计算（20 分钟阈值、不推测当前时间、进行中计时的处理）
- 重复待办「今天是否该出现、本轮是否完成」
- Notion CSV 的日期与标签解析

## 12. 需要你确认的问题

1. **部署**：Cloudflare 还是 NAS？主要在国内还是国外网络环境下用？有没有自己的域名？
2. **时区**：默认按 `Asia/Shanghai`（北京时间）划分每天，可以吗？出差到别的时区时，是否希望跟着设备时区走？
3. **跨天口径**：跨 0 点的记录按实际时间切分到两天（3.3），同意吗？
4. **重叠累加**：同时进行的记录在总时长里各自累加（3.4），同意吗？
5. **重复待办**：错过的轮次不累积（3.7），同意吗？还需要「每隔 N 天」「工作日」这类规则吗？
6. **待办的「已投入」**：重复待办显示本轮投入，一次性待办显示累计投入，可以吗？
7. **未分类**：没选标签就结束的计时，允许先存为「未分类」，还是结束时强制选择？
8. **忘记结束提醒**：计时超过多少小时提醒一次（建议 6 小时）？是否需要？
9. **备注**：记录需要备注字段吗（原型里没有放）？
